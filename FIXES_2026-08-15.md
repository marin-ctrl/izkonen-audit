Date: 2026-08-15
Scope: the two findings marked **Fixed** in the agreed remediation table.
Everything marked **Acknowledged** is deliberately NOT changed in code — see section 4.

## 1. Low-01 — anti-whale limit now derived from circulating supply

**File:** `src/IZKONEN.sol`

`MAX_WALLET` (a constant equal to 3% of `MAX_SUPPLY`) has been removed and replaced by
a basis-points constant `MAX_WALLET_BPS = 300` plus a public view `maxWallet()` returning
`(totalSupply() * MAX_WALLET_BPS) / 10_000`. `_update` now reads the live limit and reports
it in the `MaxWalletExceeded` error, whose signature is unchanged — it already carried
the limit as a parameter.

The contract NatSpec has been updated from "3% of cap" to "3% of the CIRCULATING
supply" so the code and the public documentation state the same rule.

### Consequence we want you to look at explicitly

The limit is evaluated **after** `super._update()`, so on a mint the newly minted
tokens are already part of the supply the 3% is measured against. Two effects
follow, both intended, but we would rather raise them than have them found:

1. **The first tokens must go to an exempt address.** While `totalSupply()` is 0,
   any non-exempt receiver would hold 100% of the supply, which is above 3%, and
   the transfer reverts. This is not a problem in the real flow: the first mint is
   the initial liquidity, and `IZKONENMinter`'s constructor already refuses to
   deploy unless both the treasury and the emission recipient are exempt
   (your earlier fix T-3). We added `test_FirstMintMustGoToExempt` to assert this
   deliberately rather than leave it implicit.

2. **Mint and transfer have different boundaries.** A transfer leaves the supply
   unchanged, so the exact boundary is the limit itself. A mint raises supply and
   limit together, so its boundary is 3%/97% of the pre-existing supply. The
   tests assert exact boundaries using transfers for this reason.

We also note that a burn lowers the supply and therefore lowers everyone's limit.
A holder sitting exactly at 3% before a large burn would be above the limit
afterwards. Nothing reverts on its own — the check only runs on receipt — but
their next incoming transfer would revert. We consider this acceptable and
inherent to a supply-relative limit; tell us if you disagree.

## 2. Informational-03 — `startTime_` bounded on first deployment

**File:** `src/IZKONENMinter.sol`

Added `START_TIME_GRACE_PERIOD = 7 days`, error `BadStartTime`, and a constructor
check rejecting a `startTime_` in the future or further than the grace period in
the past. The bound is applied **only to a first deployment** (`startingYearIndex_ == 0`).

A replacement minter must be given the ORIGINAL start so the yearly windows stay
aligned, and that value is legitimately far in the past — applying the same bound
there would make a correct migration impossible.

The second half of your recommendation — deriving `startTime_` from the retired
minter on-chain instead of accepting it as input — belongs to the replacement
module. That module does not exist, so per your own rule it cannot be marked
Fixed. It is recorded as a mandatory requirement in our migration runbook,
together with Informational-02, -04 and -05.

The 7-day window is deliberately non-zero: a deployment prepared and queued
through the timelock a few days earlier must still succeed.

## 3. Tests

Updated: `test/IZKONEN.t.sol`, `test/IZKONENFuzz.t.sol`.
`test/IZKONENMinter.t.sol` is unchanged (its references to the limit are in
comments only).

- A `_seedSupply()` helper mints 38.5B IZK to the exempt treasury before any
  non-exempt address receives anything, mirroring the real launch flow.
- Boundary assertions now move tokens with `transfer()` rather than `mint()`.
- `test_Constants` asserts `MAX_WALLET_BPS` and that `maxWallet()` is 0 at zero supply.
- New `test_MaxWalletGrowsWithSupply`: doubling the supply doubles the limit.
- New `test_FirstMintMustGoToExempt`: documents consequence 1 above.
- New `testFuzz_LimitAlwaysThreePercentOfSupply`: the property the old fixed
  constant failed to hold.
- Three further tests that minted straight to a non-exempt address at zero supply
  (`test_PauseBlocksTransfers`, `test_UnpauseRestoresTransfers`,
  `test_NoBlacklist_OrdinaryTransferAlwaysWorks`) now seed supply first and
  transfer instead. They would otherwise have failed under the new rule.

### What we verified, and what we did not

**Verified.** Both contracts compile cleanly with solc 0.8.26 and OpenZeppelin
5.1.0, no warnings. Bytecode: IZKONEN 7,486 → 7,585 bytes; IZKONENMinter
4,896 → 5,034 bytes.

**Not verified.** We could NOT execute the Foundry test suite. Our environment
has no network access to the Foundry distribution, so `forge` is unavailable;
solc and OpenZeppelin were obtained through npm. The updated tests are therefore
**written but not run on our side**, and we are not claiming otherwise. Please
run them as part of the fix review and tell us what fails — we will fix it.
